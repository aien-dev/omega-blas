## Results

Gate, h2 (`chip-h2-stock-all/run.log`). Each driver's route line reads `device gb10 host 0`, so every
call reached the device path.

| Driver | Netlib verdict | Calls (netlib count) | Device calls / tensor-core calls | Wall |
|---|---|---|---|---|
| sblat2 | SGEMV PASSED computational and error exits | 3461 | 3072 / 2304 | 0.989 s |
| sblat3 | SGEMM PASSED computational and error exits | 17496 | 10350 / 6750 | 2.802 s |
| c_sblat2 | cblas_sgemv PASSED column-major and row-major, and error exits | 3460 + 3460 | 6144 / 4608 | 2.278 s |
| c_sblat3 | cblas_sgemm PASSED column-major and row-major, and error exits | 17496 + 17496 | 20700 / 13500 | 6.184 s |

Device calls are fewer than netlib calls because quick returns (m or n = 0, or alpha = 0 with
beta = 1) never leave the host. That is correct BLAS behaviour, and the counters do not include
them. `gb10_host_fixed` is 0 in all four drivers: no non-finite input reached CUDApp's host repair.

Tolerance (docs/TOLERANCE.md, derived in Wolfram): for k <= 9 a correct bf16x3 result has a netlib
ratio of at most **11.19993**, below the deck's **THRESH 16.0**. The stock decks are therefore the
gate, unmodified.

Measured largest ratio, h3 (`chip-h3-thresh0/run.log`): SGEMV **1.61** (sblat2, and c_sblat2 in
both orders) and SGEMM **1.87** (sblat3, and c_sblat3 in both orders). On the host, the same
measurement gave 1.48 / 1.51 for SGEMV and 0.00 for SGEMM (`host/host-thresh0.log`).

## Negative controls

- h4, mutant 1 (CUDApp drops the last k element): all four drivers FATAL. It never reached the
  tensor core (`gb10_core_calls 0`): the first failing call has k = 1, which leaves the core no work.
- h5, mutant 2 (CUDApp forces op(B) = N): all four FATAL, after 97 tensor-core calls (sblat2 and
  c_sblat2) and 73 (sblat3 and c_sblat3). This is the control that exercises the chip.
- h5, mutant 4 (CUDApp forces beta = 0): all four FATAL on their first beta != 0 call, before any
  tensor-core call.
- h6, device evidence (`chip-h6-strace/strace-summary.txt`): during a passing sblat2 run, the process
  opened `/dev/nvidia0` 2 times, `/dev/nvidia-uvm` 2 times and `/dev/nvidiactl` 2315 times, and made
  18508 ioctls. [INFERENCE] The per-call control-handle opens look like CUDApp's per-call buffer
  setup and probably account for most of the per-call time below. Not profiled.

## Batched, strided and single f32 products (tests/gb10/batched.c)

There are 46 cases: strided batches of 3 in both layouts and all four transpose pairs, with shapes
(M,N,K) of (1,1,1), (3,5,2), (9,7,9), (16,13,16) and (4,6,0), and ld padding plus gaps between
batches. Two cases have overlapping C (stride 0, beta 0: the last problem wins). Two use pointer
arrays. One is `omb_gemm_ex` with a row bias and one is bf16, and both must stay on the host. Each
case checks every element against a double reference within the derived limit (device route 5.70,
host route 9.51; docs/TOLERANCE.md), checks that no element outside the products moved, and
checks the predicted route-counter movement.

- Chip h7 (`chip-h7-batched/run.log`): 46 of 46 pass. Largest ratio: device route **1.116**, host
  route 0.832. Routes: host 2, gb10 52 (40 strided batches in one call each, plus 2 x 3
  overlapping and 2 x 3 pointer problems), 108 tensor-core calls.
- Host, with the HMMA model in place of the chip (`host/batched-model.log`): 46 of 46 pass, with
  the same 1.116 / 0.832 and the same route and core counts. Host path on both builds
  (`host/batched-gb10build-host.log`, `host/batched-default-host.log`): 46 of 46 pass, largest
  ratio 1.330, routes host 134 gb10 0.
- Negative controls. Chip h8, CUDApp mutant 2: 16 cases fail, exit 1. On the model, CUDApp
  mutant 1: 36 fail; mutant 2: 16 fail; mutant 4: 42 fail. Mutant 5 changes only the fp8
  block-scale path and passes (0 fail), as expected.
- Library-side mutants, planted in a throwaway copy of `src/omegablas.c` and built `GB10=1`, run on
  the model:
  - op(A) and op(B) swapped in the gemm_ex mapping (`host/libmutant-opswap.diff`): two cases fail
    on their values, then gemm_ex rejects a call with BAD_ARGS and the process aborts with exit
    134.
  - stride_a and stride_b swapped (`host/libmutant-strideswap.txt`): gemm_ex rejects the first
    batched call and the process aborts with exit 134.

  Neither result is silent.

## NOT_RUN

- Large-k device numerics (k > 16, where the fixed netlib THRESH 16 no longer bounds a correct
  result; docs/TOLERANCE.md).
- `omb_gemm_ex` f32 with a fused epilogue on the device: by design it stays on the host
  (exercised as a host-route case above).
- Throughput at large shapes, and repeated timing runs.
- The python and DLPack binding against `build-gb10`, and `tests/smoke.py` on the device path
  (its limits are not derived for the device; docs/TOLERANCE.md).
